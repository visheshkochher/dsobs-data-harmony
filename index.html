The Doon School Old Boys' Society A data project: cleaning and harmonising the member register

An aristocracy of service begins with knowing who we are.

One clear record for every Dosco

Since John Martyn's first Dosco Register, the Society's records have been kept by many hands. This project turns close to 9,000 tangled rows into one trustworthy record for each of roughly 6,000 Old Boys, using reasoning models that never see a real name.

The register as it stands

The same Old Boy appears several times, in capitals in an old record and again in a newer form, with each version disagreeing a little. Values sit in the wrong columns: a date of birth in the address, a father's name among hobbies. Phone numbers are written five ways and dates three ways.

It is the kind of mess that looks as if it needs months of manual entry. It doesn't. And until it is fixed, simple questions go unanswered, such as which Old Boys in Singapore have offered to mentor, or where this year's Rose Bowl should be posted.

Privacy, by design

This is personal information belonging to thousands of Old Boys, and the method is built around that.

Before any model reads a row, every name, street, company, phone number and email is replaced on one laptop with a code made from a passphrase only the custodian knows. Reasoning models do the reading and placing on coded rows, and the results are decoded back on the same laptop. Dates, cities, school numbers and Houses stay readable, so the model can still make sense of the row.

Manual data entryTwo hired operators with full sight of every member's name, address and phone number, for a month, on machines the Society doesn't control.
This approachOne custodian on one machine, under a written undertaking. The cloud sees codes only, and the working data is deleted on completion.

The same surname gets the same code everywhere, so the model can still tell that two rows belong to one family. Change the passphrase and every code changes. This runs in your browser; nothing you type leaves it.

How the register is rebuilt

Five steps, from a tangled sheet to records the Society can rely on.

  1. Understand what is there

    Every column is read for what it actually holds against what it claims to hold, and how often values have wandered. The Society gets a factual picture of its own records, which it has never had.

  2. Put every value in its place

    A reasoning model reads each coded row the way a sharp-memoried Old Boy would. It recognises that a value sitting under "batch" is really a House, that a cell of digits is a phone number, or that a note in the margin says the whole row has slipped one column. Code then checks that whatever it placed really exists in that row.

    Interests: "Father V.K. Mehra (212 K-1951)"toa relative, House K, batch 1951
    Address: "3/14/1961"todate of birth

  3. One standard for everything

    Where the Society's own notes give a rule, plain code applies it the same way every time. Dates follow the dots-and-slashes convention the data owners described. Places are checked against every state and country in the register. Phone numbers keep their country code in a separate field.

  4. Many rows, one Old Boy

    Rows that belong to the same person are brought together: same school number and surname, or the same name with a shared email or phone. Brothers who share a House and batch stay apart. The newest information wins, older rows fill the gaps, and nothing is thrown away.

    When rows disagree on something that matters, such as a batch, both values are kept side by side with the evidence, for a person to decide.

  5. When in doubt, ask a person

    Records the pipeline cannot settle with confidence are never guessed at. They go into a review file with the suggested value alongside, for someone nominated by the Society to decide. Only genuine disagreements reach that file: rows giving different batches, a death recorded without evidence, two rows that may or may not be the same man. Editorial control stays with DSOBS.

What a living register makes possible

Once relatives carry a school number, House and batch, the register stops being a list and becomes a network of fathers and sons, brothers and cousins. Each record also carries a career, a city and a willingness to help.

Keyed pseudonymisation

Codes are HMAC-SHA256 digests under a key derived with scrypt from the custodian's passphrase. The code book is a vault encrypted with that passphrase. The pipeline refuses to send any file that still holds an email or a long number in clear.

Reasoning models, held to account

Models answer in a fixed structure, so a field can never hold a stray explanation. Every value they report is checked against its source row, and anything invented is rejected and asked again.

Rules where rules exist

Dates, school terms, House codes, Rose Bowl choices and phone formats follow fixed rules in code, so results are identical on every run. A place engine covers 49 countries and learns each PIN code's city from the register itself.

A second reading

Records with loose ends are read again with all of that person's rows at once. Fixes are accepted only if every word comes from his own rows, and never touch identity fields such as school number, batch, House or date of birth.

Triage, not noise

An editable policy decides what reaches a human. Disagreements the code can prove go to review. The model's own remarks and natural vagueness in job titles stay as notes.

Stop, resume, re-run

Every answer is stored locally, so a rerun costs nothing and an interrupted run carries on. The register is processed in ranges with a prompt before each, and the ranges are stitched back together with duplicates removed.

Prompt caching and batch processing

The shared instructions in every request, about 5,000 tokens, are cached at a tenth of the price. Requests are sent together at half price.

Built to be run again

Two operators would produce a clean file once. A pipeline can be re-run on the next export, on every new "update your record" submission, or on any future migration. The Society owns it.
